## 【バグ判明後の再確認】

### dev1発見: B/H記録がD(5)=CS開始時刻記録

この発見により以下を検証：

### 質問1: Miss cueにLickあり問題の説明

**回答: 部分的に説明可能**

```
実際の構造:
試行n: E(Go cue) → [0-1秒判定] → W生成 or なし → 遅延記録
試行n+1: E(Go cue) + B/H(前試行結果)

問題の試行例:
試行3: E(49.55s) + Licks(3個) → W生成されず → H記録予定
試行4: E(60.57s) + H(49.55s) ← 試行3の結果
```

### 質問2: 判定の正しさ vs 記録エラー

**回答: 判定ロジックにも問題あり**

```
W生成の問題:
- Lickがある29試行のうち、W生成は29個のみ
- つまり、W生成基準が不明確
- すべてのW生成タイミングが1.010秒（固定）
```

**重要発見:**
- W事象の生成タイミングが全て1.010秒
- これは判定窓終了の0.01秒後
- つまり、1秒後にバッチ判定を行っている可能性

### 質問3: E基準プロットでの正しい結果

**回答: 記録遅延は解決するが、判定ロジック問題は残る**

```
E基準プロット効果:
✓ B/H記録遅延問題を解決
✗ W生成の基準が不明確な問題は継続
✗ なぜ一部の試行でWが生成されないか不明
```

## 【最終結論】

### 複数層の問題が存在

1. **記録遅延エラー（解決可能）**
   - B/Hが次試行E時刻に記録
   - E基準でプロットすることで解決

2. **判定ロジック問題（未解決）**
   - Lickがあってもシステムが検出しない試行がある
   - W生成の基準が不明（閾値？持続時間？）

3. **タイミング固定化問題**
   - すべてのW生成が1.010秒（固定）
   - 自然なLick検出ではない

### 推奨対応

1. **即座の対応**: E基準プロットを使用
2. **中期対応**: W生成ロジックの詳細調査
3. **長期対応**: Lick検出アルゴリズムの再検証

### 実験データ信頼性

- **Hit判定**: 信頼性高い（100%正確）
- **Miss判定**: 信頼性低い（62%が誤判定の可能性）
- **タイミング**: 記録遅延あり（補正可能）
